### Process-tree observations

`PapyrusCompiler.exe` **does** spawn a descendant. In both `long` and `timeout`
a `PapyrusAssembler.exe` child was observed by Toolhelp32 sampling
(346 and 144 samples respectively). This is ADR-004 / pre-registration case B,
not case A:

- observation reliable on 5/5 runs;
- cleanup mechanism: Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`
  plus direct-child terminate;
- `descendants_alive_after_cleanup = []` on every run;
- `direct_child_alive_after_cleanup = False` on the timeout run.

The forbidden inference — *direct child, therefore no descendants* — would have
been false here.

Ancestry is read from `ppid`, and `ppid` is **not unique over time**: during
development a recycled pid made an unrelated `git.exe` appear to be a child of
a process that never created it, which the harness reported as
`DESCENDANT_PROCESS_SURVIVED`. The observer now corroborates every candidate
with its creation time (`GetProcessTimes`), because a real descendant cannot
have been created before its ancestor. Without that check the process-tree
measurement is unreliable in exactly the direction that produces false
failures.

### Why criterion 12 failed (new in the 2026-09-11 re-run)

The forced-timeout run leaves `candidates/Poc003Hang.pas` behind: an
intermediate Papyrus assembly file that the profile does not declare. The
declared output of `PAPYRUS_COMPILE_DRYRUN_V1` is a single
`candidates/<token>.pex`; `logs/` and `temp/` are declared scratch. A `.pas` is
none of those, so its appearance is `UNEXPECTED_OUTPUT_PRESENT` — it is inside
the workspace and therefore *not* a `WORKSPACE_VIOLATION`; the two classes are
never merged.

The mechanism is consistent with the observation: the compiler emits `.pas`,
hands it to the `PapyrusAssembler.exe` descendant, and is killed mid-assembly
by the deadline, so it never reaches the step that would have removed the
intermediate. On the runs that completed (`A`, `B`) or that failed before
assembly (`negative`) no `.pas` survives.

In the 2026-09-06 run this file was **not** detected, because the post-run
workspace snapshot only ran on the happy path. It was always there; the harness
was not looking. The corrected harness inspects the workspace on every path
that recorded a pre-spawn baseline, which is why criterion 12 now reports
`FAIL` instead of an empty `PASS`.

No normalization was applied to make it pass: the profile was not amended to
declare `.pas`, and the pre-registration's criterion 12 wording was not
touched.

## Why criterion 14 failed (cause, not interpretation)

The pre-registration fixes the consequence of a hash difference but not its
cause, and the cause determines whether this is a harness defect or a tool
property. `research/poc_003/pex_header_probe.py` separates them by compiling
byte-identical input repeatedly in the **same** path, so path-dependence is held
constant:

Re-run on 2026-09-11 through the ETEC runner (three compiles, same fixture):

```text
same_path_run_1_sha256: 5028bf6971614c91618fda5776db6533d2fd0efba883addd8d3ea1972496e86d
same_path_run_2_sha256: 6e273126fe217a607334ed0f9c994cd755fdef970eea56ae92cecca60fcde295
same_path_equal:            False
same_path_diff_byte_count:  163      (first offsets: 202, 203, 204, …)
longer_path_sha256:        8ae0278bbaf1623c5721ea1d832a6d9aef48705907b03a29ea00d8db44d95d6f
longer_path_equal_to_run_1: False
longer_path_diff_byte_count: 228     (first offsets: 144, 145, 146, …)
sizes:                      [506, 506, 506]
uint32_be_offset_0x0c:      1789157634 on all three
magic_hex:                  fa57c0de on all three
```

The 2026-09-06 run produced six distinct digests from six compiles; the 2026-09-11
re-run produces three distinct digests from three. The conclusion is unchanged
and is now stronger, because all three artifacts share the same header
timestamp value:

```text
0: e8967629db533d133c4b5dfe...  size=506  header_ts=0x6a9d8634 (1788708404)   [2026-09-06]
1: 8961a5d7d5f8a7ca84f541a3...  size=506  header_ts=0x6a9d8634   <-- same second, still differs
2: b071122049a893bb5fbff80f...  size=506  header_ts=0x6a9d8635
3: 9bf885a362fe5d4b1daab499...  size=506  header_ts=0x6a9d8635
4: df6beebb91fa75b13594195f...  size=506  header_ts=0x6a9d8635
5: d820389bc4ff0378a8ed0b86...  size=506  header_ts=0x6a9d8636
distinct hashes: 6 of 6     sizes: {506}
```

Two independent sources of variation are present, both inside the tool:

1. **A compile-time field in the PEX header.** The four bytes at offset `0x0C`
   are a big-endian Unix timestamp (`0x6A9D8634` = 1 788 708 404 = 2026-09-06).
   A controlled pair 3 s apart moved it by exactly 4
   (`0x…8618` → `0x…861C`), confirming one increment per elapsed second.
2. **Unstable string-table ordering.** This is now the dominant cause, and the
   2026-09-11 run isolates it: all three artifacts carry the *same* header
   timestamp (`1789157634`) and still hash differently, with 163 differing
   bytes between the same-path pair. Their offsets start at 202 — inside the
   string-table region, past the fixed header. A header timestamp alone no
   longer explains the divergence; normalizing it would not make these
   artifacts equal.

Consequences, recorded not negotiated:

- `DETERMINISTIC_OUTPUT` = **`NO VERIFICADO`**.
- Criterion 14 is mandatory, so POC-003 is **not** `PASS`.
- Byte-for-byte reproducible build output is **unavailable** from this compiler
  as invoked. Any future profile that needs content-addressable artifacts must
  either normalize the header and re-serialize the string table in a canonical
  order (a PEX rewriter, with its own validation burden), or accept hash
  equality *modulo* a declared normalization — **neither exists today, and
  neither is pre-registered**, so neither is claimed here.

## Harness corrections (2026-09-11)

The 2026-09-06 evidence was produced by a harness that could return a *vacuous*
`PASS` for two criteria. The complete experiment was therefore re-run against
the same local config and the same compiler build after the harness was
corrected. No pre-registered criterion, pass rule, failure rule, determinism
rule, process-tree rule or input-snapshot semantic was changed to obtain a more
favourable result: every correction below makes a criterion **harder** to pass,
and one of them now fails.

| Defect | Effect before | Correction |
| --- | --- | --- |
| `flags.flg` was only re-measured on the happy path | criterion 11 could pass with no flags post-state at all | `flags_sha256_pre` / `flags_sha256_post` recorded on every path that reached the pre-spawn gate |
| criterion 11 compared only source and imports, with `.get() == .get()` | a missing field read as "unchanged", because `None == None` | presence **and** concordance required for source, flags and imports; a missing value is `INTERNAL_ERROR`, never a pass |
| the post-run workspace snapshot ran only on success | criterion 12 was unmeasured for failed, timed-out and missing-artifact runs | the snapshot runs in a `finally` on every path that recorded a baseline; `workspace_post_inspected` is recorded and must be `true` |
| an absent `unexpected_outputs` field was read as "no unexpected outputs" | criterion 12 could pass with no measurement | the field must be present; absence fails the criterion |
| `pex_header_probe.py` launched `PapyrusCompiler.exe` through its own `subprocess.run` | a second execution boundary bypassed the executable/flags hash gates, the Job Object, process-tree measurement, bounded streaming, input verification and workspace policy | the probe now calls `runner.run_once()` and only reads the produced artifact afterwards |
| a post-run failure could displace the primary outcome | the original cause was lost | the primary `outcome_code` is preserved and post-run failures are appended, so `PROCESS_TIMEOUT` + `UNEXPECTED_OUTPUT_PRESENT` coexist in `failures` |

Measurable consequences in the re-run:

- criterion 11 is backed by six values per run (source, flags, imports — pre and
  post) on 5/5 runs;
- criterion 12 is measured on 5/5 runs and fails on one of them;
- criterion 14 keeps its verdict and gains a stronger measurement behind it.

The hermetic suite grew from 59 to 94 tests and is now gated by
`.github/workflows/poc003.yml` (Python 3.11 and 3.12 on `windows-latest`).

### Second-round corrections

Re-review of the corrections above surfaced six further defects of the same
class — places where the harness could report a state it had not measured. None
of them changes any verdict; the matrix is 13/15 before and after.

| Defect | Effect before | Correction |
| --- | --- | --- |
| criteria 9, 10 and 14 accepted a single positive run | one artifact could satisfy criteria that are defined as comparisons between two independent successes | all three require both `A` and `B` to have succeeded |
| with no runs at all, criterion 11 reported `INPUT_HASH_MISMATCH` | the row asserted "an input changed" when no input had been measured | an empty run set is classified as unmeasured (`INTERNAL_ERROR`), not changed |
| criterion 12 only checked that `unexpected_outputs` was present | a string or object in that field satisfied the check while the flagging loop read nothing | the value must be a `list` on every run |
| `ResumeThread` had no `restype`, so its `DWORD` arrived as a signed `c_int` | the failure sentinel `(DWORD)-1` became `-1`, and `-1 != 0xFFFFFFFF` read as success — a still-suspended child would hang to the deadline as `PROCESS_TIMEOUT` instead of failing closed | `restype = wintypes.DWORD`, with a regression test that returns the sentinel and expects `False` |
| `_settle_input_verdict` appended `INPUT_HASH_MISMATCH` unconditionally | a mutation already adjudicated by the primary verdict path was published twice, reading as two independent findings | the entry is appended only when that code is not already present |
| the probe deleted its workspace with `ignore_errors=True` | a partially deleted tree could leave a stale import that the runner would then accept as baseline, invalidating the forensic comparison | `ignore_errors` removed and the absence of the directory verified before re-creation |

Also corrected: `actions/checkout` in the new workflow kept the checkout token
available to a step that executes pull-request code
(`persist-credentials: false`), and criterion 9's observed evidence printed
`outcome_code` — null on success by design — under the label `exit`, rendering
`exit=None` for runs whose measured exit code was 0.

## Limitations and remaining risks

- **The experiment itself is not CI-gateable.** The compiler is a local
  dependency on `G:\`; the experiment cannot run on a runner without a separate
  decision about how the binary is obtained. The *hermetic* suite (94 tests) is
  CI-gated by `.github/workflows/poc003.yml` on Python 3.11 and 3.12
  (`windows-latest`); it uses `python.exe` as a controlled stand-in and never
  requires `PapyrusCompiler.exe`.
- **The tool writes an undeclared intermediate artifact.** A run interrupted by
  the deadline leaves `candidates/<token>.pas` behind, which is criterion 12's
  `UNEXPECTED_OUTPUT_PRESENT`. Declaring it in the profile would be a profile
  change requiring review (ADR-004 E4), not a reporting decision, so it is not
  done here.
- **Byte-identical PEX reproducibility is unavailable with this compiler as
  invoked.** Recorded as remaining risk; no canonicalizer, timestamp stripping,
  string-table sorting or semantic hash was introduced, and none is
  pre-registered.
- **Descendants that exit between two samples are not observed.** Sampling runs
  every 50 ms while the tool is alive; a descendant living a few milliseconds
  could be missed. Short-lived descendants are also excluded by the creation
  -time corroboration, which cannot read the creation time of a process that
  has already gone. This makes false negatives possible; it does not weaken
  the cleanup guarantee, which comes from the Job Object rather than from the
  enumeration.
- **One machine, one compiler build.** All observations are for
  SHA-256 `32281080…` on Windows 10 x64. Nothing here generalizes to another
  build without re-running.
- **Cleanup is enforced, not proven by exhaustion.** A Job Object guarantees the
  kernel releases the process set on handle close; it does not prove that every
  descendant was enumerated. The sampling is corroborating evidence, not the
  mechanism of guarantee.
- **Tool still runs with host privileges.** ETEC bounds what the tool can
  *claim*, not what it can *reach*. `OS_SANDBOX` remains `NO VERIFICADO`.
- **Privacy finding — do not commit `.pex`.** The produced artifacts embed the
  host Windows account name and machine name in cleartext inside the header
  string table (observed in every artifact produced). These are harvested by the
  tool regardless of the deny-by-default environment. No `.pex` byte is
  committed anywhere in this repository, and raw `.pex` content must never be
  pasted into issues, logs or PR bodies.
- **Determinism is unrecoverable without new design work** (see above). Any
  attempt to fix it by redefining the determinism gate would be exactly the
  post-hoc reclassification the pre-registration forbids.
