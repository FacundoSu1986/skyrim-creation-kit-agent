### Process-tree observations

`PapyrusCompiler.exe` **does** spawn a descendant. In both `long` and `timeout`
a `PapyrusAssembler.exe` child was observed by Toolhelp32 sampling
(326 and 142 samples respectively). This is ADR-004 / pre-registration case B,
not case A:

- observation reliable on 5/5 runs;
- cleanup mechanism: Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`
  plus direct-child terminate;
- `descendants_alive_after_cleanup = []` on every run;
- `direct_child_alive_after_cleanup = False` on the timeout run.

The forbidden inference — *direct child, therefore no descendants* — would have
been false here.

Ancestry is read from `ppid`, and `ppid` is **not unique over time**: during
development a recycled pid made an unrelated `git.exe` appear to be a child of
a process that never created it, which the harness reported as
`DESCENDANT_PROCESS_SURVIVED`. The observer now corroborates every candidate
with its creation time (`GetProcessTimes`), because a real descendant cannot
have been created before its ancestor. Without that check the process-tree
measurement is unreliable in exactly the direction that produces false
failures.

## Why criterion 14 failed (cause, not interpretation)

The pre-registration fixes the consequence of a hash difference but not its
cause, and the cause determines whether this is a harness defect or a tool
property. `research/poc_003/pex_header_probe.py` separates them by compiling
byte-identical input repeatedly in the **same** path, so path-dependence is held
constant:

```text
0: e8967629db533d133c4b5dfe...  size=506  header_ts=0x6a9d8634 (1788708404)
1: 8961a5d7d5f8a7ca84f541a3...  size=506  header_ts=0x6a9d8634   <-- same second, still differs
2: b071122049a893bb5fbff80f...  size=506  header_ts=0x6a9d8635
3: 9bf885a362fe5d4b1daab499...  size=506  header_ts=0x6a9d8635
4: df6beebb91fa75b13594195f...  size=506  header_ts=0x6a9d8635
5: d820389bc4ff0378a8ed0b86...  size=506  header_ts=0x6a9d8636
distinct hashes: 6 of 6     sizes: {506}
```

Two independent sources of variation are present, both inside the tool:

1. **A compile-time field in the PEX header.** The four bytes at offset `0x0C`
   are a big-endian Unix timestamp (`0x6A9D8634` = 1 788 708 404 = 2026-09-06).
   A controlled pair 3 s apart moved it by exactly 4
   (`0x…8618` → `0x…861C`), confirming one increment per elapsed second.
2. **Unstable string-table ordering.** Runs 0 and 1 share the same timestamp
   yet still hash differently; differing byte counts between same-path pairs
   ranged from 1 to 163, all inside the string table region.

Consequences, recorded not negotiated:

- `DETERMINISTIC_OUTPUT` = **`NO VERIFICADO`**.
- Criterion 14 is mandatory, so POC-003 is **not** `PASS`.
- Byte-for-byte reproducible build output is **unavailable** from this compiler
  as invoked. Any future profile that needs content-addressable artifacts must
  either normalize the header and re-serialize the string table in a canonical
  order (a PEX rewriter, with its own validation burden), or accept hash
  equality *modulo* a declared normalization — **neither exists today, and
  neither is pre-registered**, so neither is claimed here.

## Limitations and remaining risks

- **Not CI-gateable.** The compiler is a local dependency on `G:\`; the
  experiment cannot run on a runner without a separate decision about how the
  binary is obtained. The committed unit suite (59 tests) is hermetic and uses
  `python.exe` as a stand-in.
- **Descendants that exit between two samples are not observed.** Sampling runs
  every 50 ms while the tool is alive; a descendant living a few milliseconds
  could be missed. Short-lived descendants are also excluded by the creation
  -time corroboration, which cannot read the creation time of a process that
  has already gone. This makes false negatives possible; it does not weaken
  the cleanup guarantee, which comes from the Job Object rather than from the
  enumeration.
- **One machine, one compiler build.** All observations are for
  SHA-256 `32281080…` on Windows 10 x64. Nothing here generalizes to another
  build without re-running.
- **Cleanup is enforced, not proven by exhaustion.** A Job Object guarantees the
  kernel releases the process set on handle close; it does not prove that every
  descendant was enumerated. The sampling is corroborating evidence, not the
  mechanism of guarantee.
- **Tool still runs with host privileges.** ETEC bounds what the tool can
  *claim*, not what it can *reach*. `OS_SANDBOX` remains `NO VERIFICADO`.
- **Privacy finding — do not commit `.pex`.** The produced artifacts embed the
  host Windows account name and machine name in cleartext inside the header
  string table (observed in every artifact produced). These are harvested by the
  tool regardless of the deny-by-default environment. No `.pex` byte is
  committed anywhere in this repository, and raw `.pex` content must never be
  pasted into issues, logs or PR bodies.
- **Determinism is unrecoverable without new design work** (see above). Any
  attempt to fix it by redefining the determinism gate would be exactly the
  post-hoc reclassification the pre-registration forbids.
